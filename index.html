How I think about agents

The way I've found this works is basically the way a good team already runs. A capable model as the manager, cheaper models doing the legwork, and a person at the top holding the accountability. Reviewing everything at the end doesn't hold up. After twenty correct outputs, review turns into a reflex and the twenty-first error sails through. So the system brings the judgement calls forward as they come up, and remembers the answer.

01 Building

Three systems, designed and shipped end to end.

Oracle, then Vedas 2025 to now in production

An AI agent team for an accountancy firm.

Fifteen stalled draft agents became one router in front of eighteen specialist lanes. Staff brief it like a junior and it routes itself. Now being rebuilt as the firm's own product on a custom harness, with the working rules enforced in code: the manager model can't do the juniors' legwork, memory saves need the user's word-for-word approval, and anything leaving the system needs human sign-off.

What it actually does

The VAT return auditor runs a tab-by-tab audit of Xero VAT exports against HMRC rules. The accounts-preparation agent runs a three-way reconciliation, from bank to ledger to trial balance, and raises a suspense report for anything unresolved. The client-onboarding agent builds a client's KYC and permanent file through a guided interview, auto-filling from firm records and Companies House. Job-card automation fills job-setup templates from prior-year data. Alfred, an onboarding and support agent that routes staff to the right tool, was the single biggest adoption win in staff testing.

Two design rules that came out of incidents

An overloaded combined agent hung under real data load. Root-caused to turn-size overload, split into two purpose-bound agents joined by a shared handover artefact. The rule that stuck: separate by function, bound each turn. And every agent drafts for staff review; nothing auto-sends or auto-files.

beau.quest Jan to Feb 2026 shipped to beta

A matching app that watches how you react, instead of asking who you are.

Users play through AI-generated social simulations and react instinctively to moments that reveal who they really are, while a weighted identity graph learns their personality over time. Built solo through to a working beta with real users, then wound down once it had taught me what it was for.

The thinking behind it

Show, don't tell

People reveal who they are through instinctive reactions, not self-reported bios. The "Dojo" simulation embeds abstract psychological dimensions in naturalistic scenarios. Users never see the underlying model.

Identity as a living graph

Traits, values, interests and vices sit on weighted spectra in a Neo4j graph, decaying over a 90-day half-life so the system always reflects who a user is now. Matching runs through a three-stage funnel that uses attachment-theory heuristics.

Engagement by design

Profiles unlock progressively based on conversation quality ("Fog of War"). A credit economy ties real AI costs to user-facing energy, creating a natural usage cadence without runaway spend.

gonzo.guide 2026 paused, relaunch planned

A travel engine that finds the places guidebooks don't know about.

Six personas argue over the answer, the model searches in each city's own language, and every place is checked against Google Maps before it's allowed to be recommended. Born at the Cerebral Valley "Zero to Agent" hackathon with Google DeepMind and Vercel, then expanded across Telegram, Discord and web.

The thinking behind it

Six lenses, one debate

Users pick from six AI personas: Local, Plot Twist, Foodie, Hangover, Bougie, Budget. Each one surfaces different places. "Council Mode" pits two or three personas against each other in a multi-turn debate, and a synthesis call picks the winner.

Grounded, not hallucinated

Every recommendation is verified real and open via Google Maps grounding before it's shown. The model searches in each city's own language to surface what locals actually discuss, and adjusts for the weather in real time.

Automation Project Manager

Innovi Advisors London

Sole owner of the firm's AI programme: took the agent suite from a stalled discovery exercise to a tested multi-agent system spanning two platforms, then migrated it across platforms as 40+ modular skills. Now rebuilding it as the firm's own product on a custom harness built on pi, with custom MCP servers connecting the firm's systems and the working rules enforced in code.

Read the full story

Discovery and approval

  • Interviewed the firm's partners and audited 15 draft AI agents already built in Gemini Enterprise, alongside the existing stack (Microsoft 365, FYI Docs, Xero).
  • Diagnosed the recurring faults: wrong-ecosystem connectors, inconsistent prompt structure, overlapping scope. The intent underneath was clear: single-source grounding, mandatory clarifying questions, citation discipline, plain-English output.
  • Presented a phased blueprint to the partners. They approved it, and it became the basis for consolidating 15 drafts into six tested, production-shaped agents.

Architecture

  • Designed a knowledge-store grounding architecture that turns authoritative sources (HMRC, FRC, ACCA, ICAEW, Companies House, Charity Commission) into curated markdown knowledge bases, so every answer is citeable.
  • Found and fixed a live reliability failure: an overloaded combined agent hanging under real data load. Root-caused to turn-size overload and split into two purpose-bound agents joined by a shared handover artefact. The standing rule since: separate by function, bound each turn.
  • Designed Oracle, a single router in front of 18+ flattened specialist subagents, so staff no longer need to know which agent to pick.
  • Human-in-the-loop guardrails throughout: agents draft for staff review and never auto-send or auto-file.

Platforms and migration

  • Built and tested the suite in Gemini Enterprise's no-code Agent Designer, then migrated it entirely to Claude (Projects, Skills, Cowork), rebuilding 18+ subagents as 40+ modular skills. That unlocked reliable file generation the Gemini platform couldn't produce.
  • Integrated a pre-built Xero MCP server for live ledger access, with the FYI document API integration underway.

Vedas, the firm's own product (Jul 2026 to now)

  • Rebuilding the proven system on a custom harness built on pi, an open-source agent runtime, because the commercial platforms could only request the working rules in prompts. Here they're enforced in code: the manager model can't do the juniors' legwork, memory saves need the user's word-for-word approval, and anything leaving the system needs human sign-off.
  • Built custom MCP servers on the firm's own infrastructure: the practice management and document systems, Microsoft 365, and a deterministic calculation service, so every figure is computed exactly rather than by a language model.
  • First full accounts-preparation job ran end to end on the new build in August 2026: working papers with every figure traced to source, and an adversarial AI review pass before any human review.
